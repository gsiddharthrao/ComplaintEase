## 2. Summary of Confirmed Defects Fixed Across the Remediation Branch

| ID | Layer | Defect / Vulnerability | Root Cause | Fix Implemented | Verification |
|---|---|---|---|---|---|
| **D-01** | Database (`008` -> `010`) | Public sign-up role privilege escalation | `handle_new_user()` trusted `NEW.raw_user_meta_data->>'role'` during public registration | `010_security_workflow_hardening.sql` Section 1 hardcodes `'employee'` on sign-up and revokes `EXECUTE` on `handle_new_user()` from `anon`, `authenticated`, and `public` | Verified by Supabase Post-Migration 010 Query + `challenger-2-adversarial.test.ts` |
| **D-02** | Database (`006` -> `010`) | Self-service profile column escalation (`role`, `department_id`, `id`, `created_at`) | PostgreSQL RLS (`profiles_update_own`) is row-level, allowing users to update any column on their own row | `trg_protect_profile_sensitive_columns` (`protect_profile_sensitive_columns()`) raises SQLSTATE `42501` using null-safe `IS DISTINCT FROM` checks when non-admins modify sensitive columns | Verified by Supabase Post-Migration 010 Query (`auth_can_call_profile_trigger = false`) + `security-fixes.test.ts` |
| **D-03** | Database & API (`007` -> `010`, `attachments.ts`) | Bucket-wide Storage read/upload exposure & BOLA on attachment confirmation | `storage_read_authenticated` allowed any authenticated user to read any object in `attachments`; confirmation did not verify path ownership | Replaced broad policies with 3 complaint-scoped `storage.objects` policies (`storage_attachments_select_scoped`, `storage_attachments_insert_scoped`, `storage_attachments_delete_scoped`); enforced `<user_id>/<complaint_id>/<filename>`, `..` rejection, MIME whitelist, and 10 MB cap in `attachments.ts` | Verified by Supabase Post-Migration 010 Query (`scoped_storage_policies = 3`) + `security-fixes.test.ts` |
| **D-04** | Database & API (`004` -> `010`, `complaints.ts`) | Service-role RLS bypass (`getAdminClient()`) during complaint creation | `POST /api/v1/complaints` used `getAdminClient()` to insert initial `status_history` row | Removed `getAdminClient()` from user request handlers; added `AFTER INSERT` trigger `trg_complaint_initial_history` (`record_initial_complaint_status_history()`) | Verified by code audit + `concurrency.test.ts` |
| **D-05** | Database, Shared, API, Web (`004` -> `010`, `enums.ts`) | State machine drift & non-terminal `rejected` transitions | `004_functions.sql` had 11 transitions while `009` added transitions out of `rejected` (24 total in DB before Migration 010) | Synchronized `allowed_transitions` to the exact 23 canonical transitions in `@complaintease/shared`, with 0 outgoing transitions from terminal states (`closed`, `rejected`) | Verified in Supabase SQL Editor (`24 -> 23` total, `terminal_transitions = 0`) + `state-machine.test.ts` |
| **D-06** | Database, API, Web (`010`, `complaints.ts`, `ComplaintDetail.tsx`, `AdminPanel.tsx`) | Non-atomic specialist assignment & ignored transition errors | API previously ran separate queries to deactivate old assignments, insert new assignment, and optionally transition status | Created `assign_specialist(p_complaint_id, p_assigned_to, p_note, p_expected_version)` RPC with `FOR UPDATE` lock, OCC check, terminal state guard (`P0001`), and atomic assignment + transition | Verified RPC creation & `anon_can_assign = false` in Supabase SQL Editor + `concurrency.test.ts` |
| **D-07** | API & Database (`complaints.ts`, `error-handler.ts`) | Optimistic concurrency control (`expected_version`) bypass on transitions | Transition route previously re-queried current version instead of passing client `expected_version` | Passed validated `req.body.expected_version` directly to `transition_complaint()`; mapped `P0003` to HTTP `409 Conflict` | Verified by `concurrency.test.ts` & `error-handler.test.ts` |
| **D-08** | Web & API (`NewComplaint.tsx`, `AttachmentsList.tsx`) | Base64 Data URL storage in `complaints.image_url` | New complaints encoded images as large base64 strings directly in PostgreSQL text columns | Standardized new complaint uploads on two-stage signed Supabase Storage upload + confirmation with recoverable UI retry state while keeping legacy `image_url` read compatibility | Verified by `workflow-and-env.test.ts` & production Vite build |
| **D-09** | Web & API (`AdminPanel.tsx`, `EmployeeDashboard.tsx`, `ComplaintDetail.tsx`, `app.ts`) | 3-second polling loops exhausting Express rate limiter | Frontend polled every 3s across multiple queries, triggering `429 Too Many Requests` | Removed 3s polling; standardized on Supabase Realtime (`useRealtime.ts`) query invalidation + conservative 60s fallback poll + tiered Express rate limiters (`50/15m` auth/mutation, `300/15m` general) with `trust proxy = 1` | Verified by `workflow-and-env.test.ts` |
| **D-10** | Web & API (`api-client.ts`, `AdminPanel.tsx`) | White-screen crash on Admin Panel "Immutable Audit Trail" tab | `GET /api/v1/admin/audit-logs` returns `{ data: [...], total_count }`, and `fetchWithAuth()` returned the wrapper object instead of the array when `total_count` was present, causing `auditLogs.map is not a function` | Unwrapped `res.data` in `api.admin.getAuditLogs()` (`apps/web/src/lib/api-client.ts`), added defensive `Array.isArray` normalization and loading/empty states in `AdminPanel.tsx`, and added regression test coverage in `security-fixes.test.ts` | Verified by `security-fixes.test.ts` & `pnpm -r build` |
| **D-11 (Gap A)** | Database, API, Web (`011_specialist_assignment_hardening.sql`, `ComplaintDetail.tsx`, `AdminPanel.tsx`) | `assign_specialist()` checked target profile existence but did not enforce target `role = 'employee'` | `assign_specialist()` in Migration 010 selected `v_target_profile` without verifying `v_target_profile.role`, allowing an administrator profile to be assigned as a field specialist if called directly | Created Migration `011_specialist_assignment_hardening.sql` to reject any target profile where `role IS DISTINCT FROM 'employee'` with SQLSTATE `P0001` (HTTP 400) while keeping `P0002` (HTTP 404) for nonexistent targets; filtered UI specialist dropdowns to `u.role === 'employee'` | Verified locally by `concurrency.test.ts`; SQL Test 17A/17B added to `rls_and_concurrency_test.sql` (pending Migration 011 execution in Supabase) |
| **D-12 (Gap B)** | Shared, API, Web, Database (`transition.schema.ts`, `complaints.ts`, `ComplaintDetail.tsx`, `011_specialist_assignment_hardening.sql`) | `assignSchema` allowed optional `expected_version` and `assign_specialist()` skipped OCC when `p_expected_version` was `NULL` | `expected_version` had `.optional()` in `assignSchema` and `IF p_expected_version IS NOT NULL` in `assign_specialist()`, allowing callers omitting `expected_version` to bypass concurrency protection | Made `expected_version: z.number().int().min(1)` mandatory in `assignSchema`, required in `ComplaintDetail.tsx`/`AdminPanel.tsx`/`complaints.ts`, and enforced `IF p_expected_version IS NULL OR p_expected_version < 1 THEN RAISE EXCEPTION ... USING ERRCODE = 'P0003'` in Migration `011_specialist_assignment_hardening.sql` | Verified locally by `validators.test.ts` & `concurrency.test.ts`; SQL Test 18A/18B/18C added to `rls_and_concurrency_test.sql` (pending Migration 011 execution in Supabase) |
